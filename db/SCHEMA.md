# SCHEMA.md — 왜 이 모양인가

정본은 `schema.sql` 이다. **이 문서는 컬럼 표를 다시 그리지 않는다.**
값 목록이 궁금하면 `schema.sql` 의 `CHECK` 을 보면 된다. 여기 적힌 순간
동기화 지점이 하나 생기고, 그게 이 문서 세트를 다시 만든 이유다.

- 이력 → `DECISIONS.md`
- 조정 가능한 **수치** → `tuning.yaml` (코드가 읽는 정본)
- 그 수치의 **근거** → `TUNING.md`
- 마이그레이션 절차 → `migrations/README.md`
- subject 의 **정의**(포함 예·경계) → 3단계 분류 프롬프트 문서
- subject 의 **명단** → `seed.sql`

---

## 왜 SQLite 인가

**쓰기 주체가 하나이기 때문이다.** collector 가 DB 를 독점하고, n8n 도
blogstudio 도 HTTP 로만 붙는다. SQLite 의 유일한 실질 약점이 동시 접근인데
그게 구조적으로 사라진다. 백업은 파일 복사고 운영 부담이 없다.

blogstudio 에 읽기 API 를 만드는 비용이 붙지만 어차피 필요했다 —
`rank` 를 저장하지 않고 조회할 때 조립하기로 했으므로(아래) 그 조립 코드가
곧 조회 계층이다. 파일을 직접 읽게 하면 blogstudio 가 그걸 중복 구현한다.

**Postgres 로 갈 트리거 둘.** 지금은 아니지만 이때는 다시 본다.

1. 임베딩 pre-filter 가 필요해질 때 (5단계에서 유보한 것). pgvector 면 공짜고
   SQLite 는 `sqlite-vec` 확장을 얹어야 한다
2. 쓰기 주체가 둘이 될 때. "유일 소유자" 전제가 깨지면 근거 전체가 무너진다

## 저장 기준 — 배치를 넘어 재사용되는가

```

```

## 일간과 주간을 가른다

```
매일   수집 → 본문 → 분류 → 분석          기사당 독립 · 멱등
──────────────────────────────────────  ← 저장 기준선과 같은 선이다
매주   클러스터링 → 소재 → topics          여러 기사를 가로지름
```

우연이 아니다. **기사 단위로 닫히는 일은 도착하는 대로 처리해도 결과가 같고,
여러 기사를 가로지르는 일만 시간창이 필요하다.** 실무적으로도 월요일에 수백
건을 한꺼번에 물지 않고 매일 30~40건씩 나눠 문다.

주 1회로 묶으면서 얻는 것이 하나 더 있다 — **열도 신호에 변별력이 생긴다.**
매일 돌리면 `hot_recent_72h`·`hot_span_hours` 가 전부 비슷하게 나와 신호가
죽는다. 7일 창이어야 "월요일에 터져 목요일까지 이어진 이슈"와 "일요일 단발"이
갈린다.

### 중복 소재 문제가 여기서 해소된다

배치가 **미소비 기사만** 가져가므로 기사 집합이 배치끼리 겹치지 않는다.
**배치 간** 중복은 이걸로 끝난다.

> **정정 (2026-08-25).** 이전 판에 "같은 기사가 두 소재의 근거가 되는 일이
> 구조적으로 불가능"이라고 적었는데 **틀렸다.** `batch_id` 가 막는 것은
> 다음 배치에서 다시 후보가 되는 것뿐이고, **같은 배치 안에서** 한 기사를
> 여러 `topics.article_ids` 에 넣는 것은 스키마가 막지 않는다.
>
> 배치 내 중복을 막는 것은 스키마가 아니라 **5단계의 완전 분할 불변식**이다 —
> 프롬프트가 "한 기사는 둘 이상의 이슈에 넣지 않는다"를 지시하고, 검증 코드가
> `입력 aid 집합 == 모든 issue.article_ids 의 합집합` 을 검사해 중복 id 를
> 뒤 이슈에서 제거한다. **DB 가 아니라 파이프라인이 보장한다.**

### 소재 1 : N 기사 — 기사 쪽에서 보면 N : 1 이다

v1 스키마 문서는 이 관계를 "진짜 N:M(관통 소재)"이라고 적었다. **그 문장도
이제 낡았다.** 5단계가 한 기사 한 이슈를 강제하고 배치가 기사를 소비하므로,
현재 설계에서 기사 하나는 **소재 최대 하나**에 들어간다.

N:M 이 되는 경로는 하나뿐이다 — **"이슈를 발생시킨 핵심 기사"와 "설명을
보강하는 참고 기사"를 나누고, 후자를 여러 소재에서 재사용**하는 정책.
그 정책을 도입하면 `article_ids` JSON 으로는 FK·중복·역할을 보장할 수 없어
`topic_articles` 연결 테이블이 필요해진다.

**지금은 도입하지 않는다.** 보강 기사가 실제로 필요한지 확인된 바 없고,
필요해지는 시점에 만들면 JSON 을 읽어 옮기는 마이그레이션 한 번이면 된다.

> 표기 주의: "기사 → 소재 1:N" 이라고 쓰면 **기사 하나가 여러 소재에 들어간다**는
> 반대 뜻이 된다. 정확히는 `소재 1 : N 기사` 이고 `기사 N : 1 소재` 다.

그래서 `topics.issue_signal` 로 문자열 비교를 하던 중복 회피는 **폐기했다.**
LLM 이 매번 새로 짓는 30자를 비교하는 방식이라 애초에 잘 붙지 않았고
(v2→v3 에서 같은 묶음의 이름이 실제로 바뀌었다), 이제 필요도 없다.
`issue_signal` 은 판정 키가 아니라 **기록용 필드**로만 남는다.

**이슈 반복은 허용한다.** 다른 기사로 같은 흐름을 다시 쓰는 것은 중복이 아니라
후속이다. 막지 않기로 했고, 별도 장치를 두지 않는다. 같은 글이 반복되면 사람이
`rejected` 로 거른다.

## 소비 마커 — `batch_id` 와 `consume_reason`

`batch_id IS NULL` 이 곧 "아직 소재로 안 쓰였다"이다. 별도 불린을 두지 않는다.

### 왜 `topics.article_ids` 역조회로 안 되나

**소재가 안 나온 기사가 있다.** 분류 실패·무이슈·분석 실패는 어느 소재에도
안 들어가므로 역조회로는 영원히 미소비다. 매주 후보에 다시 오른다.

### 왜 끝에 찍나

배치 하나에 LLM 콜이 40~50 번 돈다. 시작할 때 찍으면 중간에 터진 배치의
기사가 **영구 증발한다** — `batch_id` 는 있는데 소재는 없고, 재실행해도
소비 처리라 다시 안 잡힌다.

`topics` 저장과 **같은 트랜잭션에서** 찍는다. 터지면 `batch_id` 가 `NULL` 로
남아 다음 실행에 그대로 다시 잡히고, 배치는 `state='aborted'` 로 남는다.
멱등성이 공짜로 생긴다.

### 창 밖 기사도 같이 찍는다

7일보다 오래된 미소비 기사를 안 찍으면 매주 재검사되면서 창 조건에 계속
걸려 영원히 안 뽑힌다. 미소비 더미가 무한히 쌓이고 조회만 무거워진다.

그래서 배치 끝에 두 문장을 돌린다.

```sql
-- 클러스터링에 실제로 들어간 것
UPDATE articles SET batch_id = :b, consume_reason = 'clustered'
 WHERE id IN (:ids);

-- 창 밖으로 밀린 것. state·subject·signal 을 안 보는 것이 의도다 —
-- 분류 실패든 무이슈든 시간이 지나면 전부 정리된다.
-- 단 collected_at 상한은 반드시 있어야 한다
UPDATE articles SET batch_id = :b, consume_reason = 'stale'
 WHERE batch_id IS NULL
   AND collected_at <= :as_of          -- ← 배치 도중 도착한 기사를 삼키지 않는다
   AND published_at <  :window_from;
```

`collected_at <= :as_of` 가 빠지면 **배치가 도는 동안 늦게 수집된 과거 기사까지
이 배치가 소비해 버린다.** 후보 조회에는 넣고 여기엔 안 넣으면 경계가 한쪽만
닫힌다.

**기사가 죽는 게 아니다.** `article_analysis` 는 그대로 남는다.

> **정정 (2026-08-25).** 이전 판은 "subject 를 늘리거나 창을 넓히면
> 재사용된다"고만 적었다. **자동으로는 안 돌아온다** — 후보 조회가
> `batch_id IS NULL` 을 보므로 소비된 기사는 무엇을 바꾸든 후보에서 빠진 채다.
> 남는 것은 분석 결과지 후보 자격이 아니다. 되살리는 경로는 아직 없다(아래).

### 소비 마커와 사람의 판정이 충돌한다 — 아직 안 풀었다

아래 `state_tags` 표는 `too_broad`(너무 넓음) 로 거절해도 "articles 는 그대로"
라고 말한다. 그런데 **배치가 이미 그 기사들을 소비했으므로 그대로 두면 다시
후보가 되지 않는다.** 표와 실제 동작이 어긋나 있다.

한때 `requeue`(=`batch_id`·`consume_reason` 을 NULL 로 되돌리기)를 넣으려 했는데
**그것만으로는 동작이 완성되지 않는다.** 되돌려도 다음 배치에서는 이미 7일 창
밖이라 곧바로 `stale` 로 죽는다. 창을 우회하는 상태를 하나 더 만들면 때울 수는
있지만, 그건 문제를 잘못 푼 것이다 —

> **`too_broad` 는 "다시 수집하라"가 아니라 "그 이슈를 쪼개라"는 뜻이다.**

필요한 건 재수집이 아니라 **재분할**이다. 같은 기사 묶음으로 5단계를 다시
돌리되 더 잘게 쪼개라고 지시하는 별도 경로. 그걸 설계하기 전에 컬럼과 설정만
먼저 만들면 반쯤 작동하는 기능이 남는다.

**그래서 MVP 에서 뺐다.** `requeued_at` 컬럼도, `tuning.yaml` 의 requeue 설정도
없다. `keywords` 사전을 "없는 기능을 위한 테이블"이라고 안 만든 것과 같은
논리다. 현재 동작은 이렇게 읽으면 된다.

```
too_broad 로 거절   topics.state='rejected'
                   근거 기사는 소비된 채 남는다 — 되살리는 경로가 아직 없다
```

SQLite 는 `ALTER TABLE ADD COLUMN` 이 싸다. 재분할을 설계할 때 붙인다.

근거: 오래된 해설이 "지금 움직이는 이슈"의 열도에 끼면 안 된다. 5단계 v2
실측에서 시간창 필터가 6건(전부 Carbon Brief)을 걸렀고, 같은 원칙을 배치
단위로 올린 것이다.

## 테이블별 함정

### subjects

**순수 분류표다.** 서비스·키워드·설명을 여기 넣지 않는다. 넣으면 질의마다
필터가 붙고 주제 사전이 관리 불가능해진다.

소재 생성 단위가 아니라 **이슈 클러스터링을 돌릴 묶음을 나누는 보조
인덱스**다. LLM 에게 "500건에서 주제를 찾아라"를 안 시키기 위한 것이다.
그래서 입도가 굵어야 한다 — 너무 잘면 이슈가 갈릴 여지가 없고, 너무 굵으면
한 주제에 기사가 몰려 콜이 터진다.

**이름은 두 곳에 산다.** `seed.sql`(정본)과 3단계 분류 프롬프트의 subjects
목록. 이름을 바꾸면 같은 커밋에서 둘 다 고친다. 어긋나면 게이트가 정상
분류를 전부 `id·name 불일치` 로 강등시킨다. 실제로 한 번 났던 사고다.

> n8n 게이트 노드의 `SUBJECTS` 상수는 DB 가 붙으면 조회로 대체한다.
> 그때 동기화 지점이 셋에서 둘로 줄어든다.

### sources

`paywall` 기본값이 `unknown` 인 이유 — **`none` 을 기본으로 두면 확인 안 한
걸 무료로 취급하게 된다.** 임팩트온에서 실제로 당했다. RSS 만 보고 무료로
판단했는데 기사 페이지는 200자에서 끊기고 단건결제였다.

`can_seed` 와 `can_cite` 는 다른 질문이다.

```
can_seed   이 기사로 소재 후보를 만들 수 있나
can_cite   독자가 그 링크를 열어 확인할 수 있나
```

`can_cite=0` 은 **독자에게 보여줄 링크 목록에 안 들어간다**는 뜻이다. 열 수 없는
링크를 다는 것은 "출처가 있다"를 흉내만 내는 것이다.

`topics.article_ids` 와 헷갈리면 안 된다 — 그쪽은 클러스터 구성 기사 **전체**라
`can_cite=0` 도 들어간다. 링크 목록은 조회할 때 `sources` 조인으로 만든다.

`empty_streak` 이 헬스체크의 전부다. **RSS 가 200 을 주면서 8개월째 같은
기사를 주는 매체가 실제로 있었다**(한국에너지신문). `last_ok_at` 으로는 절대
못 잡는다. 부처 도메인이 바뀌는 것도 같은 신호로 잡힌다.

`config` 의 절충 — **값만 config 에, 로직은 어댑터 코드에.** 선택자·페이징을
데이터로 옮기면 CMS 가 바뀌어도 코드를 안 고치지만, 오타가 런타임까지 안
잡힌다. 로직 조각을 config 에 넣어 우회하지 않는다.

어댑터는 **자기 네임스페이스만** 읽는다. `crawl` 은 `kind` 와 직교다 —
`rss+crawl`(환경일보)은 `crawl` 블록만, `board+crawl`(KEITI)은 둘 다 갖는다.
`kind × body_mode` 조합 검증은 DDL 이 아니라 **collector 가 한다** — SQLite
CHECK 수정은 테이블 재생성이라 비싸고, collector 가 유일 소유자라 우회
경로가 없으며, 파이썬 검증은 테스트로 잠긴다.

### articles

**`published_at` 이 NOT NULL 이 아니라 CHECK 인 이유.** 발행시각을 모르는
기사도 `excluded` 로 **저장해야 한다.** 저장을 포기하면 `url_key` 중복 차단이
안 걸려 같은 기사가 매 폴링마다 재등장한다. 그렇다고 NOT NULL 이면 그 행의
insert 자체가 터진다. 그래서 정상 기사에만 강제한다. 열도 계산은 어차피
`state='active'` 만 보므로 NULL 이 섞일 길이 없다.

**`url_key` 정규화** — scheme 무시 · host 소문자 · `www.` 제거 · fragment 제거
· 경로 끝 슬래시 제거 · 추적 파라미터만 제거(`utm_*`·`fbclid`·`gclid`·
`igshid`·`mc_cid`·`mc_eid`·`ref`).

**쿼리를 통째로 털면 안 된다.** 국내 언론사 CMS 는 `?idxno=19040` 처럼
쿼리에 기사 id 가 있다. 털면 한 매체의 모든 기사가 같은 키가 된다.
n8n Code 노드에는 URL 생성자가 없어 정규식으로 파싱한다.

중복 제거는 `INSERT OR IGNORE` 로 끝난다.

**`press` 는 복사하고 `can_cite` 는 조인한다.** press 는 수집 시점의 *사실*이라
소스를 지워도 남아야 하고, can_cite 는 *정책*이라 바뀌면 소급 적용되는 게 맞다.

**`primary_subject_id` — 이름에 뜻이 있다.** 기사 하나가 여러 주제를 동시에
다룰 수 있지만, 묶는 기준은 하나여야 한다. "이 기사의 모든 주제"가 아니라
소재화 묶음 기준으로 고른 대표 하나다.

`state` 가 두 값뿐인 이유 — **"소재에 묶였나"는 `state` 가 답할 질문이 아니다.**
그건 `batch_id` 와 `consume_reason` 이 답한다. `state` 에 `mapped` 같은 값을
두면 같은 사실이 두 컬럼에 살고, 둘이 어긋나는 순간 어느 쪽이 맞는지 알 수 없다.

> 이전 판은 "한 기사가 여러 소재에 걸리는 것(관통 소재)을 허용해야 하므로"라고
> 적었다. **낡은 문장이다** — 현재 완전 분할 정책에서 그 경로는 없다.

`state_reason` 은 **영문 스네이크로 통일했다.** CHECK 을 걸 값 집합에 한글
문장이 섞여 있으면 오타가 조용히 통과한다. 사람이 남기는 자유 서술은
`state_note` 로 뺐다.

### article_analysis

**왜 articles 와 나누나** — articles 는 한 번 일어난 일이라 다시 안 만들고,
분석은 프롬프트를 고치면 다시 만든다. `issue_signal` 이 클러스터링의 키라서
프롬프트를 여러 번 고칠 게 확실하다. 버전을 안 남기면 옛 분석과 새 분석이
섞인 채로 클러스터링이 돈다.

**`state` 에 pending 이 없다.** 행이 없는 것이 곧 pending 이다. 그래서 분석
대상 조회가 한 쿼리로 끝난다.

```sql
SELECT a.*
FROM articles a
LEFT JOIN article_analysis n
       ON n.article_id = a.id
      AND n.prompt_version = :v
      AND n.subject_id = a.primary_subject_id
WHERE a.state = 'active'
  AND a.primary_subject_id IS NOT NULL
  AND a.body_state IN ('full','snippet_only')
  AND (n.id IS NULL OR (n.state = 'failed' AND n.attempts < 3));
```

`n.id IS NULL` 이 **"아직 안 했음"·"프롬프트 버전이 올랐음"·"재분류로 subject
가 바뀌었음"을 동시에** 잡는다.

세 번째가 `subject_id` 스냅샷을 둔 이유다. 4단계는 `subject_name` 을
프롬프트에 넣어 분석하는데, 3단계는 버전을 저장하지 않고 최신으로 덮어쓴다
(v4 재분류에서 4·5번 기사가 실제로 이동했다). 스냅샷이 없으면 **어느 subject
전제로 만든 분석인지 알 수 없고**, UNIQUE 에 걸려 재분석도 안 된다.

`is_current` 같은 파생 플래그를 두지 않는다. 현재 버전은 코드가 아는 상수다.
파생 플래그는 언젠가 실제 최신본과 어긋난다. **옛 버전을 지우지 않는다** —
"프롬프트를 고쳤더니 어떻게 달라졌나"가 유일한 튜닝 재료다.

**`issue_signal` 검증 실패는 NULL 이다. repair 하지 않는다.** 고쳐 넣기
시작하면 "검증기가 통과시킨 값"과 "검증기가 만들어낸 값"이 섞여 클러스터링
품질을 추적할 수 없다. reject 사유는 로그에만 남긴다.

DB 컬럼에서는 **무이슈-NULL 과 거절-NULL 이 같은 NULL 이다.** 구분은 집계와
로그에서만 한다. 필요해지면 컬럼을 나눈다.

**왜 요약이 필요한가 — 숫자.** 이슈 탐지 입력이 7일치 200~280건이다. 본문
그대로면 50만 자로 한 콜에 안 들어간다. 요약 250자면 6만 자, subject 별로
나누면 콜당 5천 자. **요약은 이슈 탐지를 가능하게 하는 압축이다.**

**분석은 필터 뒤에 돈다.** 앞에 두면 탈락할 기사까지 분석한다. 그리고
필터와 분석을 한 콜로 합치지 않는다 — 필터는 `title+snippet` 으로 싸게 전건,
분석은 통과분만 본문으로 비싸게. **분석은 기사당 1콜이다.** 묶어서 보내면
LLM 이 기사 id 를 드롭한다.

### batches

**`as_of` 는 배치 시작 UTC 시각이다.** 스파이크에서는 DB 가 없어
`max(collected_at)` 으로 유도했는데, DB 가 붙으면 그럴 이유가 없고 문서마다
정의가 갈리기만 했다. 하나로 못 박는다.

`as_of` 를 저장하는 이유 — 열도가 실행 시각 기준이면 **재실행할 때마다 결과가
바뀐다.**

**그런데 `as_of` 만으로는 재현되지 않는다.** 배치가 실패한 뒤 다시 돌리는
사이에 **과거 발행 기사가 늦게 수집되면** 후보 집합에 새로 낀다. 그래서 후보
조회에 수집 시각 상한이 같이 있어야 한다.

```sql
SELECT a.id, a.press, a.published_at, n.summary, n.issue_signal, n.change_type
FROM articles a
JOIN article_analysis n
     ON n.article_id = a.id
    AND n.prompt_version   = :analyze_version
    AND n.subject_id       = a.primary_subject_id
WHERE a.batch_id IS NULL                 -- 미소비
  AND a.state = 'active'
  AND a.primary_subject_id IS NOT NULL
  AND n.state = 'done'
  AND n.issue_signal IS NOT NULL         -- 무이슈는 묶을 게 없다
  AND a.collected_at <= :as_of           -- ← 이게 없으면 재실행이 안 재현된다
  AND a.published_at >= :window_from
  AND a.published_at <  :window_to;      -- ← 미래로 잘못 파싱된 기사를 막는다
```

정확한 재현이 더 필요해지면 배치 시작 시 후보 id 를 스냅샷한다. 지금은 위
조건으로 충분하고, 스냅샷은 저장할 테이블이 하나 더 생기는 비용이 있다.

### topics

**완성된 소재만 담는다.** 6단계가 실패한 이슈는 저장하지 않는다. 그래서
`subject_id`·`business_relevance`·`hot_*`·`n_citable` 이 전부 `NOT NULL` 이고,
`article_ids` 는 빈 배열을 거부한다. 반쯤 만들어진 소재를 남기고 싶어지면
그때는 `pending` 상태를 먼저 정의해야 한다 — NULL 로 표현하면 "아직 안 됨"과
"계산했는데 0"이 같은 값이 된다.

**`issues` 테이블을 안 만들었다.** 6단계가 임계 없이 전 이슈를 소재화하므로
지금은 `이슈 ≡ topics 1행` 이다. 별도 테이블이 없어도 잃는 게 없다.

> **되살아나는 트리거: 7단계 임계를 켜는 순간.**
> 탈락 이슈가 생기면 그것들이 저장 자리를 잃는다. 임계를 정하려면 탈락선
> 아래를 봐야 하는데 그게 안 남는다. 그때 `issues` 를 만든다.

**열도 신호를 저장한다.** 합산 공식은 "소재 후보를 눈으로 본 다음 정한다"고
미뤄뒀는데, **나중에 볼 건데 저장을 안 하면 볼 게 없다.** 스파이크에서 만든
33건의 열도 신호는 이미 휘발됐다. 공식의 근거는 이 컬럼들이 쌓여야 생긴다.

**`search_demand` 는 항상 NULL 이다.** 검색량 공급원이 없다. 키워드 개수로
만든 숫자를 `search_demand` 라고 부르면 화면 보는 사람이 실제 검색량으로
받아들인다. `keywords[].volume` 의 NULL 과 0 도 같은 이유로 구별한다 —
"모름"과 "0"이 같은 값이면 점수가 조용히 거짓말을 한다.

공급원이 생기기 전까지 `final_score = business_relevance` 다. **열도 가산도
없다.** n_press=2 가 +0.1 만큼 중요하다는 근거가 아직 없고, 점수 가중치는
검증 임계와 달리 순위를 조용히 비튼다.

**`rank` 를 저장하지 않는다.** 하나를 제외하면 나머지가 다 밀린다. 조회할 때
`final_score` 정렬로 매기고, blogstudio 계약의 `rank` 는 조회 코드가 조립할 때
붙인다.

**`article_ids` 를 JSON 으로 접었다.** 근거는 현재 관계가 1:N 이기 때문이다
(위 "기사↔소재는 지금 1:N 이다"). 연결 테이블이 주는 FK·중복 방지·역할
구분이 지금은 남는 값을 못 만든다. 역방향 질의는 줄었을 뿐 없어지지 않았지만
현재 규모에선 JSON 역조회 비용을 감수할 수 있다.

**여기에는 클러스터 구성 기사가 전부 들어간다.** `can_cite=0` 기사도 포함이다 —
독자에게 보여줄 링크 목록은 별개고, `sources` 조인으로 조회할 때 만든다.
그래야 임팩트온이 유료를 풀면 과거 소재의 근거도 같이 열린다. `can_cite` 를
`topics` 에 스냅샷하면 그 소급이 막힌다(결정 #9: press 는 사실이라 복사,
can_cite 는 정책이라 조인).

```sql
SELECT t.id FROM topics t, json_each(t.article_ids) j
WHERE json_extract(j.value, '$.id') = 12;
```

아파지면 `topic_articles` 로 분리한다. JSON 을 읽어 옮기는 마이그레이션 한
번이면 끝난다.

**`state` 와 `verdict` 를 따로 두지 않는다.** `kept` 가 곧 좋다, `rejected` 가
곧 싫다다. 나누면 `state=kept + verdict=down` 같은 모순 상태가 생긴다.
`used` 는 사람이 소진시킨 것, `stale` 은 시간이 만든 것 — **`kept` 는
`stale` 이 되지 않는다.**

`state_tags` 가 제외 범위를 가른다.

어휘는 **영문 스네이크**로 고정한다(`state_reason` 과 같은 이유 — 한글 문장이
코드 값으로 섞이면 오타가 조용히 통과한다). 표시 이름은 화면이 붙이고,
`tuning.yaml` 의 `topic_reject_tags` 가 정본이다.

| 코드 | 표시 | topic | articles |
| --- | --- | --- | --- |
| `too_broad` | 너무 넓음 | rejected | **그대로** — 묶기가 잘못됐을 뿐이다 |
| `no_evidence` | 근거 댈 게 없는 주제 | rejected | **그대로** |
| `service_mismatch` | 서비스랑 안 맞음 | rejected | **excluded** |
| `already_covered` | 이미 다룬 내용 | rejected | **excluded** |
| `low_heat` | 화제성 낮음 | rejected | **그대로** |
| (사유 없음) | | rejected | **그대로** |

`low_heat` 은 열도 튜닝을 위해 새로 넣었다. `kept`/`rejected` 만 보면 서비스
직접성·근거 부족·중복이 한 덩어리로 섞여서, `hot_*` 신호가 맞는지 확인할 수
없다. **열도에 대한 사람의 판정을 따로 받아야 열도를 튜닝할 수 있다.**

**모르면 좁게 처리한다.** 잘못 제외하면 근거 하나를 덜 쓰는 게 아니라 기사가
통째로 사라진다.

| 신호 | 누가 |

| 기사 수 · 매체 수 | 코드 |
| 새로운 변화가 있었나 | 코드 — `change_type='변화'` 집계 |

**매체 편향을 조심한다.** 한 매체가 하루 25건을 쏟으면 그 주제가 늘 뜨거워
보인다. 기사 수보다 `DISTINCT press` 가 중요한 신호다.

## DB 가 안 막는 것 — collector 가 막는다

`schema.sql` 은 값의 모양을 막고, 관계의 규칙은 collector 가 막는다.
아래는 CHECK 으로 못 넣었거나 일부러 안 넣은 것들이다.

| 규칙 | 왜 DDL 이 아닌가 |
| --- | --- |
| `kind × body_mode` 유효 조합 | 새 조합이 생기는 것 = 새 어댑터가 있다는 뜻. CHECK 수정은 테이블 재생성이라 비싸다 |
| `final_score` 계산식 | 지금은 `= business_relevance` 지만 열도를 섞을 예정이다. **바뀔 게 확실한 값을 DDL 에 박지 않는다** |
| `state_tags` 어휘 고정 | JSON 배열 원소는 CHECK 에서 `json_each` 를 못 써 검사할 수 없다. 사람이 붙이는 태그라 어휘도 늘어난다 |
| 5단계 완전 분할 (한 기사 한 이슈) | 배치 내 규칙이라 행 단위 CHECK 으로 표현이 안 된다. 검증 코드가 집합 비교로 잡는다 |
| `article_ids` 원소의 FK | JSON 안이라 FK 가 안 걸린다. `topic_articles` 로 분리하면 그때 생긴다 |

collector 가 DB 유일 소유자라 우회 경로가 없고, 파이썬 검증은 테스트로
잠긴다. **막는 주체가 어디든 막히기만 하면 되는 게 아니라, 바뀔 것은 코드에
바뀌지 않을 것은 DDL 에 두는 게 기준이다.**

## 아직 안 정한 것

- **7단계 선별 임계 — 지금은 캘리브레이션 모드다.** 임계도 상한도 없이 전
  이슈를 소재화한다. 그래서 현재 상태는 "핫한 소재를 고르는 시스템"이 아니라
  **고르는 기준을 만들기 위한 데이터 수집 구조**다. 이 상태를 언제 벗어나는지는
  `TUNING.md` 의 종료 조건에 박아뒀다 — 안 정해두면 영영 캘리브레이션이다
- **열도 합산 공식.** 이제 신호가 저장되니 근거가 쌓인다
- **`business_relevance` 합본 편향.** 6단계가 소재 작성과 점수를 한 콜에
  합쳤다. 스파이크 33건에서 0.2 아래가 0건이고 최저가 0.42 였다 — 바닥이
