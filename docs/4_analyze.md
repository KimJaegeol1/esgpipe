# 4_analyze — 기사 하나를 이슈 탐지용 값으로 압축

**정본은 `prompts/4_analyze/v1/system.md` · `user.md` 다.**
이 문서는 프롬프트 전문을 복사하지 않는다.

- 어느 버전을 쓰는가 → `tuning.yaml` 의 `prompt_versions.analyze`
- 결정 이력 → `db/DECISIONS.md`
- 스키마 근거 → `db/SCHEMA.md` 의 `article_analysis`

---

## 왜 요약이 필요한가 — 숫자다

5단계 이슈 탐지의 입력이 7일치 200~280건이다. 본문 그대로면 50만 자가 넘어
한 콜에 안 들어간다. 요약 250자면 6만 자, subject 별로 나누면 콜당 5천 자.

**요약은 사람이 읽는 글이 아니라 이슈 탐지를 가능하게 하는 압축이다.**
이 출력만 읽고도 다른 기사와 같은 흐름인지 판단할 수 있어야 한다.

---

## 3단계와 다른 점 셋

**① `subject_name` 이 입력에 들어간다.** 분석이 subject 전제 아래 이뤄진다 —
같은 기사도 "탄소 산정" 관점과 "공급망 실사" 관점에서 다른 요약이 나온다.
그래서 `article_analysis` 가 `subject_id` 를 스냅샷한다(결정 #51). 3단계는
버전을 저장하지 않고 최신으로 덮어쓰므로, 스냅샷이 없으면 **어느 전제로
만든 분석인지 알 수 없고** UNIQUE 에 걸려 재분석도 막힌다.

**② 본문 전문을 보낸다.** 3단계는 600자 상한이었다(#94). "필터는 싸게
전건, 분석은 비싸게 통과분만"이 그 이유고, 여기가 "비싸게" 쪽이다.

**③ 실패가 NULL 로 남는다.** `issue_signal` 검증에 걸리면 고쳐 넣지 않고
NULL 이다. repair 하면 "검증기가 통과시킨 값"과 "검증기가 만들어낸 값"이
섞여 클러스터링 품질을 추적할 수 없다.

## 본문 상한을 두지 않는다 (v1)

Carbon Brief 가 **건수의 15% 인데 본문의 53%** 다.

```
Carbon Brief   10건  평균 13,658  최대 31,097   합계 136,581   ← 53%
나머지         56건  평균  2,163               합계 121,290
System × 66                                    합계 154,572
                                               총   412,443
```

31,097자 한 건이 임팩트온 15건 분량이다. 3단계에서 소스별 편차 18배를
균질화한 것과 같은 상황으로 보이지만 **성격이 다르다.**

**3단계는 실패가 관측됐다.** ESG Today 106자로는 제목 말고 판단할 게 없었다.
4단계는 **긴 본문이 실제로 문제인지 모른다.** 길다는 사실만 있다.

그리고 비용·컨텍스트 문제가 아니다. 41만 자면 12만 토큰 남짓이고 한도에
안 걸린다. **품질 문제인데 근거가 없다.**

### 지금 상한을 두면 첫 실험을 해석할 수 없다

Carbon Brief Q&A 의 signal 이 나쁘게 나왔을 때 —

```
원문이 너무 길어서 초점이 흐려진 것인가
앞부분만 잘라서 핵심 소주제가 사라진 것인가
```

구분이 안 된다. **상한 없는 실행이 "모델이 원문 전체를 받았을 때 어디까지
압축하는가"의 기준선**이고, 그게 있어야 나중에 상한의 효과를 비교할 수 있다.

### 첫 실행에서 남길 것

요약 노드가 건별로 이 값들을 센다.

```
press · body_chars · summary_chars · issue_signal · summary_warn · signal_rejected
```

**보는 것 둘.**

```
긴 본문일수록 summary_warn(400자 초과)이 늘어나는가
  → 늘면 긴 본문을 2~4문장으로 못 압축하는 것

긴 본문에서 issue_signal 이 넓거나 모호해지는가
  → "~관련 동향" 처럼 뭉뚱그려지면 초점이 흐려진 것
```

**실패해도 바로 `N자 상한` 으로 가지 않는다.** `Q&A: Does the world need
carbon capture` 같은 목차형·다중 쟁점 기사에 **앞부분 절단이 맞는 처리인지**
부터 판단한다 — 소주제 분리가 답일 수도 있다.

## 코드가 하는 검증

LLM 이 판정하고 collector 는 저장·검증만 한다.

| 검사 | 처리 |
| --- | --- |
| `issue_signal` 30자 초과 | **NULL. repair 안 함** + `signal_rejected` 로 집계 |
| `summary` 400자 초과 | **경고만.** 데이터는 안 건드린다 |
| `change_type` 이 3종 밖 | 저장하지 않는다 (스키마 CHECK) |
| `state='done'` 인데 `summary` NULL | 스키마 CHECK 이 막는다 |
| 같은 `(article_id, prompt_version, subject_id)` | UNIQUE. 재분석은 셋 중 하나가 바뀔 때 |

**`issue_signal` 이 NULL 인 이유는 둘이다** — 무이슈(정상 출력)와 검증 거절.
DB 컬럼에서는 같은 NULL 이고 **구분은 집계와 로그에서만 한다.** 필요해지면
컬럼을 나눈다.

`change_type` 이 3종(변화·해설·동향)인 이유 — 열도에 필요한 건 "변화가
있었나"지 형식이 아니다. 6종이면 발표/시행/개정 경계에서 흔들리고 **그
흔들림이 열도에 노이즈로 들어간다**(결정 #24).

---

## 첫 실행에서 볼 것

- **`issue_signal` NULL 비율.** 무이슈와 거절을 갈라서 본다. 거절이 많으면
  30자 상한이 아니라 프롬프트 문구를 본다
- **`change_type` 분포.** `해설` 이 압도적이면 5단계에서 열도 신호(`n_change`)가
  죽는다
- **본문 길이 vs summary 길이.** 위의 관측 기준
- **같은 subject 안에서 issue_signal 이 겹치는가.** 5단계가 묶을 수 있는지의
  선행 신호다 — 전부 제각각이면 클러스터링이 singleton 만 낸다
