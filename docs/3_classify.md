# 3_classify — 기사 하나를 subject 하나로

**정본은 `prompts/3_classify/v4/system.md` · `user.md` 다.**
이 문서는 프롬프트 전문을 복사하지 않는다 — 복사하는 순간 동기화 지점이
하나 생기고, 그게 이 레포 구조를 만든 이유다.

- 어느 버전을 쓰는가 → `tuning.yaml` 의 `prompt_versions.classify`
- subject 이름의 정본 → `db/seed.sql`
- 결정 이력 → `db/DECISIONS.md`

---

## 프롬프트를 collector 가 서빙한다

```
tuning.yaml  prompt_versions.classify: 4
      ↓
GET /prompts/classify
      ↓
prompts/3_classify/v4/{system,user}.md 를 읽어 반환
      ↓
n8n Code 노드가 자리표시자를 치환해 AI 노드에 넘긴다
```

**워크플로 JSON 안에 프롬프트 복사본을 두지 않는다.** `schema.sql` 과
마이그레이션 델타는 둘 다 필요한 산출물(하나는 새 DB, 하나는 기존 DB)이지만,
워크플로 안의 프롬프트는 **없어도 되는 파생본**이다. 같은 취급을 할 이유가
없다.

프롬프트를 자주 고치는 단계라는 것은 복사본을 둘 이유가 아니라 **동기화
실패 가능성이 가장 큰 시기**라는 뜻이다.

**n8n 화면에서 프롬프트를 보려면** AI 노드가 아니라 `GET /prompts/classify`
노드의 실행 결과를 보면 된다. 편집과 버전 비교는 레포의 md 에서 한다.

### 실행 시작에 한 번만 가져온다

기사마다 가져오면 실행 도중 파일이 바뀔 때 82건이 서로 다른 프롬프트를
쓴다. 한 번 받아 표현식으로 참조하면 그 배치는 같은 내용과 같은 해시를
쓴다.

collector 쪽에는 `@lru_cache` 를 걸지 않는다. 작은 md 를 실행당 한 번 읽는
비용은 무시할 수준이고, 캐시를 걸면 프롬프트를 고칠 때마다 재시작해야 한다.

## 자리표시자 — `{{ }}` 를 쓰지 않는다

```
[[PRESS]]  [[PUBLISHED_AT]]  [[TITLE]]  [[CLASSIFICATION_TEXT]]
```

**n8n 표현식(`{{ $json.title }}`)을 파일에 넣으면 안 된다.** HTTP 로 받아온
문자열 안의 표현식을 n8n 이 다시 평가해준다고 기대할 수 없다 — 그러면
`{{ $json.title }}` 이 리터럴로 박힌 채 LLM 에 간다.

중립적인 자리표시자를 쓰고 Code 노드가 치환하면, 정본은 레포에 있고
n8n 에는 범용 렌더링 코드만 남는다. 프롬프트를 고쳐도 워크플로를 안 건드린다.

### 렌더러가 지켜야 할 것

- **한 번의 정규식 치환**으로 처리한다. 순차 치환하면 기사 제목에 다른
  자리표시자 문자열이 들어 있을 때 재치환된다
- 렌더링 **전에** 필수 토큰이 정확히 한 번씩 있는지 검증한다

## 입력 계약

`GET /articles/pending-classify` 가 주는 값을 그대로 쓴다.

| 자리표시자 | 출처 |
| --- | --- |
| `[[PRESS]]` | `sources.press` (정본. `articles.press` 가 아니다) |
| `[[PUBLISHED_AT]]` | `articles.published_at` · ISO8601 UTC |
| `[[TITLE]]` | `articles.title` |
| `[[CLASSIFICATION_TEXT]]` | body 앞 600자, 없으면 snippet (결정 #94) |

**레이블이 `snippet` 이 아니라 `분류용 기사 텍스트` 다.** `snippet_only`
소스에서는 실제로 snippet 이 들어가므로 "본문 앞부분"이라고 부를 수 없고,
`snippet` 이라 부르면 모델이 "요약만 왔구나"로 읽는다.

### `text_truncated` 는 프롬프트에 넣지 않는다

**절단 여부는 운영·진단용 메타데이터이지 분류 판단의 입력 특성이 아니다.**
모델은 제공된 텍스트 안에서 판단한다. 알려주면 판단을 유보할 여지가 생긴다.

## subject 목록이 프롬프트에 하드코딩된 이유

충돌이 아니다. 역할이 다르다.

```
subjects 테이블   id ↔ name 의 정본. collector 가 저장할 때 대조한다
프롬프트          정의·포함 예·경계표의 정본. LLM 이 판단하는 재료다
```

`subjects` 는 **순수 분류표**라 정의를 담지 않는다(서비스·키워드·설명을
넣지 않기로 한 결정). LLM 은 후보를 알아야 고를 수 있고, 경계표가 판단의
핵심이다.

**이름의 동기화 지점은 둘이다** — `db/seed.sql` 과 이 프롬프트. 원래 셋이었고
n8n 게이트의 `SUBJECTS` 상수가 빠져 둘로 줄었다(결정 #92). 이 둘은 성격이
달라 합칠 수 없다. **이름을 바꾸면 같은 커밋에서 둘 다 고친다** — 어긋나면
collector 가 정상 분류를 전부 422 로 거부한다.

## system.md 의 문법 규칙

**`### 숫자. 이름` 형식은 subject 정의에만 쓴다.**

`prompt_validation` 이 이 형식을 정규식으로 뽑아 `subjects` 테이블과
대조한다. 다른 절에 번호를 매기면 그게 subject 로 잡혀 "DB 에 없는 id" 로
막힌다. 번호가 필요한 다른 목록은 `**1.** …` 처럼 다른 표기를 쓴다.

## 실제 LLM 입력량 — 기사 부분은 9%다

`GET /articles/pending-classify` 의 총 입력 53,086자는 **기사 부분만**이다.
System Prompt 는 기사마다 다시 들어간다.

```
System Prompt   6,753 × 82  =  553,746자
User 고정 레이블    ~60 × 82  =    4,920자
기사 입력                    =   53,086자
────────────────────────────────────────
                              611,752자      ← 기사 부분은 8.7%
```

**프롬프트를 실행당 한 번 가져오는 것은 HTTP 조회를 줄일 뿐 LLM 입력을
줄이지 않는다.** 600자 상한도 마찬가지다 — 늘리면 그만큼 늘지만, 비용을
지배하는 건 System Prompt 다.

"필터는 싸게"(결정 #18)가 여전히 맞는지는 **4단계 분석과 비교해야** 안다.
분석은 본문 전문(평균 2,000자, Carbon Brief 는 14,000자)을 보내므로
System Prompt 비중이 훨씬 낮다. 첫 실행 후 실제 토큰으로 확인한다.

## 코드가 하는 검증

`POST /articles/classify` 가 저장 전에 본다.

| 검사 | 처리 |
| --- | --- |
| `subject_id` 가 `subjects` 에 없음 | **422. 저장 안 함** |
| `subject_name` 이 왔는데 정본과 불일치 | **422. 저장 안 함** + 로그 |
| `subject_id` 가 `null` | `state_reason='subject_mapping_failed'` — 정상 출력이다 |
| `gate_result='digest'` | `state='excluded'` · `state_reason='digest'` |
| 이미 같은 결과가 저장됨 | `already_applied` · 변경 없음 |
| 이미 다른 결과가 저장됨 | **409. 변경 없음** |

동시 요청 10개를 같은 기사에 다른 subject 로 보내면 **200 하나 · 409 아홉**이
나온다. `BEGIN IMMEDIATE` 가 트랜잭션 시작에 쓰기 잠금을 잡아 `SELECT →
UPDATE` 사이에 끼어들 창이 없다.

### 프롬프트와 DB 의 subject 대조는 **요청마다** 한다

`GET /prompts/classify` 가 프롬프트를 읽은 직후 `subjects` 와 대조하고,
어긋나면 `500 prompt_subject_mismatch` 로 막는다.

**시작 시점 검증만으로는 부족하다.** 프롬프트를 캐시하지 않으므로 서비스가
뜬 뒤 `system.md` 가 수정되면 시작 검증은 통과한 상태로 잘못된 프롬프트를
계속 서빙한다 — 캐시를 안 걸기로 한 결정이 검증 위치까지 정한다.

**그렇다고 시작 검증으로 서비스를 못 뜨게 하지도 않는다.** 분류 프롬프트
하나 때문에 `/ingest` 까지 멈추면 수집도 못 한다. 실측: DB 이름을 어긋나게
두면 `/prompts/classify` 는 500, `/sources/due` 는 200 이다.

검사 넷 — 중복 id · 누락 id · 추가 id · 이름 불일치. dict 로 바로 만들면
**중복 id 가 조용히 덮어써지므로** 따로 센다. 여러 문제가 있으면 한 번에
다 보고한다 — 하나 고치고 다시 돌려 다음 걸 찾는 건 느리다.

**id↔name 불일치를 `mapping_failed` 로 강등하지 않는다(결정 #93).**
`mapping_failed` 는 "subjects 목록의 공백"을 찾는 신호인데 모델의 형식
오류를 섞으면 그 신호가 죽는다. 그리고 id 와 name 중 모델이 어느 쪽을
의도했는지 알 수 없다. 저장하지 않으면 다음 조회에 다시 잡혀 재시도된다.

불일치 로그는 버그 목록이 아니라 **경계표에 뭘 추가할지 알려주는 재료**다.
응답에 받은 이름과 정본 이름을 같이 담는 이유가 그것이다.

## 버전 규칙

**`v4` 가 실제 분류에 한 번이라도 쓰인 뒤에는 내용을 고치지 않는다.**
고쳐야 하면 `v5/` 를 새로 만들고 `tuning.yaml` 을 올린다. 그래야
`prompt_versions.classify: 4` 가 항상 하나의 고정된 내용을 가리킨다.

`GET /prompts/classify` 응답의 `sha256` 은 **식별 신호이지 불변성 강제가
아니다.** 같은 버전인데 해시가 달라졌다면 이 규칙이 깨진 것이고, 그걸
알아차릴 수단일 뿐 막아주지는 않는다.

해시에는 **파일 경계**가 들어간다. 바이트만 이어 붙이면
`system="ab"+user="c"` 와 `system="a"+user="bc"` 가 같은 `abc` 라 같은
해시가 된다(실측 확인). 파일명·NUL·길이(8바이트 big-endian)·내용을
`system.md` → `user.md` 순서로 넣는다. **순서나 이 구성을 바꾸면 해시가
달라진다.**

### v4 를 collector 서빙으로 옮기며 바뀐 것 (2026-08-25)

System Prompt 는 **한 글자도 안 고쳤다.** `snippet`·`본문`·입력 필드 설명이
한 건도 없어서 새 입력 계약과 충돌하지 않았다.

User Prompt 만 바꿨다.

```
{{ $json.press }}   → [[PRESS]]           n8n 표현식 제거
snippet:            → 분류용 기사 텍스트:   결정 #94 반영
{{ $json.snippet }} → [[CLASSIFICATION_TEXT]]
```

## 첫 실행에서 볼 것

- **`mapping_failed` 비율.** v3 에서 25/82(30%)였다. v4 는 실패 원칙을
  강화했으니 늘 수 있는데, **20% 를 넘으면 원칙 문구가 아니라 subjects
  공백(부문별 탈탄소·생물다양성)을 먼저 의심한다**
- **4번에 뭐가 모이나.** 확장 후 산림 회계(1→4)가 이동해야 정상이다.
  1↔4 경계 로그를 주시한다
- **5↔6 경계.** 이번에 처음 생겼다. 시멘트·철강 CCUS 기사에서 흔들리면
  예시를 보강한다
- **5↔11.** 5가 CCUS 를 받으면서 새로 생긴 경계다. 국가 제도·고시면 11,
  프로젝트·경제성이면 5
- **422 로그.** id↔name 불일치가 반복되면 경계표에 추가할 재료다
- **입력이 600자로 바뀐 영향.** v3 는 `snippet` 으로 돌렸다 — 환경미디어는
  1,898자, ESG Today 는 106자였다. 지금은 전부 600자라 **v3 결과와 직접
  비교할 수 없다**
